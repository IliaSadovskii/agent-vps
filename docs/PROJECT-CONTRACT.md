# Контракт проекта

Чтобы проект работал на этом сервере и с ним могли работать автономные агенты,
он должен выполнять несколько требований. Их немного, и они не зависят от стека:
контракт одинаков для Laravel, Go, Flutter или чего угодно ещё.

**Зачем.** Сервер общий, проектов много, работают с ними разные сессии агентов.
Контракт даёт единый интерфейс: не нужно читать проект, чтобы понять, как его
поднять и как прогнать тесты. И гарантирует, что проекты не подерутся за порты.

---

## Требования

### 1. Makefile с целями `up`, `down`, `test`

Обязательны всегда — это и есть интерфейс проекта.

| Цель | Что делает |
|---|---|
| `make up` | поднимает **всё** окружение: контейнеры, миграции, зависимости |
| `make down` | глушит окружение, освобождает память и порты |
| `make test` | прогоняет тесты на поднятом окружении |

Необязательные, но полезные: `shell`, `logs`, `seed`, `lint`.

У проекта без сервисов (например, мобильное приложение) `up`/`down` — заглушки:

```makefile
up:    ## тулчейны из .mise.toml
	mise install
down:  ## поднимать нечего
	@true
test:
	flutter test
```

Главное правило: **после `make up` проект работоспособен**. Если нужно вручную
дописать команду, чтобы приложение начало отвечать, — контракт не выполнен.

### 2. Порты — только через переменные

В `docker-compose.yml` порты задаются переменными со значением по умолчанию:

```yaml
ports:
  - "${APP_PORT:-8000}:8000"
```

Хардкод (`"8000:8000"`) недопустим: на сервере несколько проектов, и второй
такой просто не поднимется.

Каждому проекту выделен **блок из 10 портов**. Значения приходят из
`ports/<имя>.env` этого репозитория и дописываются в `.env` проекта
автоматически при запуске `dev-env.sh`. Имена переменных выбирает сам проект.

**Как получить блок для нового проекта** (делается в управляющей сессии `vps-main`):

1. создать `ports/<имя>.env` в репозитории `vps`;
2. взять свободный десяток (`8010`, `8020`, `8030`…) и расписать переменные;
3. выполнить `bash dev-env.sh` — он проверит пересечения и разложит порты по проектам.

### 3. `.env.example` со всеми переменными

Секреты в git не попадают, поэтому в репозитории лежит образец с пустыми
значениями. Если `.env` у проекта нет, `dev-env.sh` создаст его из `.env.example`.

### 4. `.mise.toml` — если нужны тулчейны на хосте

Платформа ставит **только менеджер версий** `mise`, но ни одного языка. Что
именно нужно проекту, объявляет сам проект:

```toml
[tools]
flutter = "3.35.0"
```

Тогда версия уезжает вместе с репозиторием на любую машину. Всё, что можно
запустить в контейнере, лучше запускать в контейнере — `.mise.toml` нужен там,
где docker не подходит (мобильная разработка и подобное).

### 5. Раздел в `CLAUDE.md` проекта

Чтобы агент не выяснял это заново каждую сессию:

```markdown
## Окружение
- `make up` — поднять, `make down` — погасить, `make test` — тесты
- Тестовая БД: <как создаётся>
- Восстановить данные: <команда>
- Секреты для локального запуска: <что нужно и откуда взять>
```

---

## Чеклист

- [ ] `make up` поднимает окружение с нуля, и приложение отвечает
- [ ] `make down` всё гасит
- [ ] `make test` проходит на чистом окружении
- [ ] порты в compose — через `${ПЕРЕМЕННАЯ:-значение}`, хардкода нет
- [ ] `.env.example` актуален, секретов в git нет
- [ ] `.mise.toml` — если нужны хостовые тулчейны
- [ ] в `CLAUDE.md` есть раздел «Окружение»

---

## Задание для агента

Открой сессию проекта (`claude-project <имя>`) и дай агенту такой запрос:

> Приведи проект к контракту разработки, он описан в
> `/home/dev/vps/docs/PROJECT-CONTRACT.md` — прочитай его целиком.
>
> Проверь по чеклисту, что уже выполнено, а что нет. Затем:
> 1. Сделай в Makefile цели `up`, `down`, `test` — так, чтобы после `make up`
>    приложение действительно отвечало, а не просто стартовали контейнеры.
> 2. Убери хардкод портов в compose, замени переменными с значением
>    по умолчанию. Сами номера портов правь только в `.env` — он не в git,
>    его заполняет платформа.
> 3. Проверь `.env.example` — там должны быть все переменные и ни одного секрета.
> 4. Если проекту нужны тулчейны на хосте (не в контейнере) — заведи `.mise.toml`
>    с точными версиями.
> 5. Допиши в `CLAUDE.md` раздел «Окружение».
>
> Проверь результат честно: `make down`, потом `make up`, потом `make test` —
> всё с нуля. Если тесты не проходят или чего-то не хватает (например, секрета
> от платного пакета) — не выдумывай обход, просто скажи, что именно нужно.
>
> Порты не выбирай сам: если они ещё не выданы, скажи об этом — блок выделяется
> в управляющей сессии сервера.

---

## Чего проект делать НЕ должен

- **Ставить что-либо на хост** (`sudo apt install`, глобальный `npm -g`). Всё
  нужное — либо в контейнере, либо через `.mise.toml`.
- **Занимать порты вне своего блока** — конфликт с соседним проектом.
- **Публиковать порты на `0.0.0.0` осознанно** — наружу проект отдаёт платформа
  через Tailscale, а firewall всё равно закроет доступ из интернета.
- **Класть секреты в git.**
