# Контракт проекта

Правила для проектов в `/projects`. Одинаковы для любого стека.
Смысл: агент не должен читать проект, чтобы понять, как его поднять и протестить.

## Требования

**1. Makefile с целями `up`, `down`, `test`**

| Цель | Что делает |
|---|---|
| `make up` | поднимает **всё** окружение и приложение |
| `make down` | гасит, освобождая память и порты |
| `make test` | прогоняет тесты |

После `make up` проект работоспособен. Нужна ещё одна команда руками — контракт не выполнен.
У проекта без сервисов `up`/`down` — заглушки (`mise install` / `@true`).

Что «работоспособен» значит на практике: **установка зависимостей, ключи приложения,
миграции и справочные данные — часть `make up`**, а не то, что человек делает потом.
Место им — в entrypoint контейнера: тогда шаги одинаковы у человека, у агента и в CI,
и не расходятся с документацией. Формулировка «сначала `make up`, потом `composer install`
и миграции» контракт не выполняет, даже если цель `up` в Makefile есть.

`make up` завершается, когда приложение реально отвечает, а не когда контейнеры созданы.
Для docker — healthcheck и `docker compose up -d --wait`. Иначе следующая команда
(тесты, миграции) стучится в ещё не поднявшийся сервис и падает на ровном месте.

`make test` работает на своих данных и не трогает базу разработки — проверь это
явно, а не по намерению. Типовая ловушка: переменные, заданные контейнеру в
`environment`, оказываются сильнее настроек тестового окружения, и тесты уходят
в рабочую базу. В `environment` держи только адреса сервисов внутри docker-сети,
остальное — в `.env`.

`make down` данные не удаляет — гасит. Для полного сноса вместе с томами заводи
отдельную цель `make clean`: снос данных не должен случаться у того, кто просто
освобождал память.

**2. Порты — через переменные, без хардкода**

```yaml
ports:
  - "${APP_PORT:-8000}:8000"
```

Номера приходят из блока, выделенного проекту, — их подставляет платформа в `.env`.
Хардкод `"8000:8000"` сломает соседний проект.

Правило распространяется на **все** сервисы, включая вспомогательные — поисковый
движок, почтовую заглушку, панель админки. Порт из блока стоит тратить только на то,
к чему ходишь с хоста; остальное общается внутри docker-сети и наружу не публикуется.
Сервис, который сегодня не нужен, лучше убрать из автозапуска (в docker — `profiles`),
чем держать впустую: память на сервере общая.

**3. `restart: unless-stopped` у всех постоянных сервисов**

Сервер перезагружается — после обновления ядра, по воле провайдера, просто так.
Без политики перезапуска проект после этого лежит, и узнаёшь об этом, когда
полез работать.

`unless-stopped`, а не `always`: контейнер, который остановили намеренно
(`make down`), должен остаться остановленным, иначе `down` перестаёт что-либо
значить. Разовым задачам — миграциям, сборкам — политика не нужна.

**4. Пароли к БД и кэшу — обязательные переменные, без дефолтов**

```yaml
POSTGRES_PASSWORD: "${DB_PASSWORD:?DB_PASSWORD не задан в .env}"
```

`:-password` вместо `:?` — тихий фолбэк: проект молча поднимется со словарным
паролем, и однажды это уедет туда, где порт БД виден не только твоей машине.
Пусть лучше упадёт сразу и скажет, чего не хватает.

Redis тоже: без `requirepass` он пускает любого, а через `CONFIG SET dir` из
него пишутся файлы — это захват машины, а не утечка кэша.

**5. `.env.example` со всеми переменными, без секретов**

Он не документация, а рабочая заготовка: платформа делает из него `.env`, когда
проект клонируют впервые. Значения должны соответствовать окружению из
`docker-compose.yml` — устаревший `.env.example` ломает первый запуск на новой машине,
и обнаруживается это в самый неудобный момент.

**Файлы, которые контейнер пишет в смонтированный код** (`vendor/`, `node_modules/`,
логи), должны принадлежать пользователю хоста, а не root — иначе после первого же
`make up` человек не сможет их править. В docker это build-arg с UID/GID и `USER`
в Dockerfile.

**6. `.mise.toml` — если нужны тулчейны на хосте**

```toml
[tools]
flutter = "3.35.0"
```

Только для того, что нельзя запустить в контейнере (мобильная разработка и подобное).

**7. Раздел «Окружение» в `CLAUDE.md` проекта**

Команды запуска, где тестовая БД, как восстановить данные, какие нужны секреты.

## Нельзя

- ставить что-либо на хост (`sudo apt install`, `npm -g`) — только контейнер или `.mise.toml`;
- занимать порты вне своего блока;
- класть секреты в git.

## Чеклист

- [ ] `make up` на чистой машине (без зависимостей и томов) → приложение отвечает
- [ ] `make up` возвращает управление только после готовности приложения
- [ ] `make down` гасит всё; `make clean` — сносит и данные
- [ ] `make test` проходит и **не трогает данные разработки** (отдельная тестовая база)
- [ ] порты в compose — переменными, у всех сервисов
- [ ] `restart: unless-stopped` у постоянных сервисов
- [ ] пароли БД и Redis — обязательные переменные (`:?`), Redis с `requirepass`
- [ ] `.env.example` актуален, секретов в git нет
- [ ] файлы, созданные контейнером в коде, принадлежат пользователю хоста
- [ ] `.mise.toml` — если нужен хостовый тулчейн
- [ ] в `CLAUDE.md` есть раздел «Окружение»

## Задание для агента

В сессии проекта:

> Приведи проект к контракту: `/home/dev/vps/docs/PROJECT-CONTRACT.md` — прочитай целиком.
> Пройди по чеклисту, сделай недостающее. Порты сам не выбирай: если их ещё нет в `.env`,
> скажи — блок выделяется в управляющей сессии сервера.
> Проверь честно: `make down` → `make up` → `make test` с нуля. Если чего-то не хватает
> (например, секрета от платного пакета) — не выдумывай обход, скажи, что нужно.
